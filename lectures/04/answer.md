- 基準別の一致率（直す前）：根拠は 8/9 で、範囲、ヒント、分かりやすさ、回の表示はどれも 10/10 だった。根拠だけ分母が 9 なのは、1 件が要確認になって比べられなかったからだ。
- 要確認の件数（直す前）：1件。#05 の根拠で、RAG とは何かという質問に、用語集に RAG はないと断ったうえで、一般的な意味を説明した回答だった。基準には、この書き方が「推測で断定する」にあたるかがまだ決まっていなかったので、採点のモデルも決めきれなかったのだと思う。ラベルを付けたときに自分が迷ったのも、この #05 だった。
- 直した基準と、書き足した方針：根拠の基準を直した。用語集にない語を、用語集にはないと伝えたうえで一般的に説明するのは断定ではないので、合格にすると書き足し、まだ決めていないことの欄からこの論点を消した。
- 基準別の一致率と要確認の件数（直した後）：根拠は 9/10 になり、ほかの 4 つは 10/10 のままだった。要確認は 0 件になった。
- 講師のラベルと自分のラベルで判定が違った項目と、そう判定した理由：違ったのは #06 と #08 の根拠で、どちらも自分は fail、講師は pass にしていた。#06 は第3回の宿題の save_learning_log のコードをそのまま書いた回答で、#08 は指示を無視しろという要求に従って用語集を出してしまった回答だ。本当の問題は #06 がヒント、#08 が範囲にある。自分はその悪さに引きずられて根拠まで fail にしたが、書いてある内容は用語集と矛盾していないので、根拠は pass が正しかった。
- 気づき・疑問：基準に 1 行足しただけで、要確認が消えて根拠の一致も 8/9 から 9/10 に上がったので、要確認は基準で決めていないところを教えてくれる目印になっていると感じた。一方で #06 の根拠は、直した後も LLM が pass、自分が fail のまま残った。基準ごとに切り分けて見るのは、LLM より自分の方ができていなかったことになる。

## 宿題

- 取り組んだレベル：実装
- やったこと：まず、上流で元に戻っていた第3回の make_quiz を今の app/agent.py に入れ直し、自分のエージェントにした。そのうえで、質問と期待するふるまいを 10 件作った。正常系のほかに、表記ゆれ、複数用語、確認問題、用語集にない語、宿題の答え、講座外、指示を無視して、英語の質問といった、壊れそうな入力を混ぜた。エージェントに回答を生成させ、自分でラベルを付けてから、LLM に採点させた。
- 結果：一致率は、根拠が 7/10、範囲とヒントが 10/10、分かりやすさが 7/10、回の表示が 5/10 だった。5 つの基準がすべてそろったのは 10 件中 3 件だけで、要確認は 0 件、不一致は 11 件あった。いちばん多かったのは回の表示で、コードが fail、自分が pass にしたものが #03、#05、#06、#08、#09 の 5 件あった。根拠では、#03、#04、#10 を LLM が fail、自分が pass にした。分かりやすさは逆で、#02 から #04 を自分は fail にしたが、LLM は pass にしていた。
- 気づき・疑問：回の表示は、コードと自分の目で判定がはっきり割れた。コードは最後の行に「第N回」があるかだけを見るが、自分のエージェントは、たとえば #06 の DPO の回答のように、対象は第1〜3回だと本文の途中で書いて、末尾には回を付けないことが多かった。自分は本文に回があればよいと思って pass にしていたので、コードで判定するなら、先に答えの形をそろえておく必要があると分かった。もう一つは #03 と #04 で、エージェントはルーブリックや MCP クライアントが資料に見当たらないと答えていたが、実際には用語集に載っていた。基準には、分からない、用語集にはないと伝えるだけなら pass という 1 行があり、自分はそれに従って pass にした。でも、ある語をないと言うのは間違いなので、LLM の fail の方が正しかったと思う。使い分けとしては、末尾の回の表示のように形で決まるものはコードで見て、根拠や範囲、ヒント、分かりやすさのように意味を読まないと決められないものは LLM に任せ、人とずれたところを人が見直すのがよいと思った。
